# 第一题：端到端执行方案
- 此需求 从技术层面简单来讲 主要问题是 性能优化及代码优化
- 前提 背景需求准确 且 毫无描述问题
- ！！！注意事项：
  1. **支付逻辑不可轻易变更，谨慎操作。**
  2. **seo相关代码可根据需求调整，不可去除。**
  3. **保证首屏内容稳定页面结构不可变动。**
  4. **多语言易出错，需人工核对每一项的正确性。**
  5. **改动位置较多，需要注意各个页面用户状态一致性。**

## 一、需求拆解与风险识别

### 1.1 需求拆解

将整体目标拆为 **5 个工作流**，每个工作流独立交付、独立验证：

| #  | 工作流              | 核心产出                         | 依赖关系             |
| -- | ---------------- | ---------------------------- | ---------------- |
| W1 | **组件层统一**        | 抽出跨站点共享组件库（monorepo package） | 无前置依赖            |
| W2 | **SSR / 渲染策略分层** | 明确每个区块的渲染模式并落地               | 依赖 W1 组件定义       |
| W3 | **LCP 性能专项优化**   | 移动端 LCP ≤ 2.0s               | 依赖 W2 渲染策略       |
| W4 | **第三方脚本治理**      | 营销脚本 / 支付 SDK 加载策略重构         | 与 W3 并行          |
| W5 | **多站点批量同步机制**    | CI 驱动的跨站点变更分发 + 回归测试         | 依赖 W1 \~ W4 全部完成 |

每个工作流再按 **设计 → 实现 → 验证 → 灰度 → 全量** 五步推进。

### 1.2 业务关键路径

按"出问题会影响收入或不可逆"排序：

1. **支付入口完整性** — 支付按钮渲染、点击链路、SDK 初始化必须零回归。
2. **SEO 结构化数据** — JSON-LD、meta 标签、canonical、hreflang 不能变，否则索引排名直接受损。
3. **首屏内容稳定性（CLS）** — 产品图、标题、价格、CTA 按钮不能发生布局偏移。
4. **多语言正确性** — 尤其是 hreflang 和 SSR 输出的语言内容，错误会导致爬虫索引混乱。
5. **用户状态一致性** — 登录态、会员价、购物车状态在 SSR 和 hydration 之间不能闪烁或错乱。

### 1.3 必须提前识别的风险

| 风险                                                  | 影响                            | 识别手段                                          |
| --------------------------------------------------- | ----------------------------- | --------------------------------------------- |
| SSR hydration mismatch                              | 首屏闪烁、CLS 飙升、SEO 降级            | 逐组件审查 `onMounted` vs `setup` 中的环境判断           |
| 第三方脚本阻塞 LCP                                         | LCP 不降反升                      | 用 Chrome DevTools Network 瀑布图 + Lighthouse 归因 |
| 缓存击穿 / stale 内容                                     | 用户看到旧价格或旧文案                   | 压测 + CDN 缓存命中率监控                              |
| 组件库版本不同步                                            | 站点 A 用 v1.2、站点 B 用 v1.0，行为不一致 | Monorepo 强制统一版本 + Renovate 自动升级               |
| 支付 SDK 与 CSP 策略冲突                                   | 支付弹窗白屏                        | 每个站点单独 CSP 白名单回归测试                            |
| 多语言 SSR 输出与客户端不一致（一般应有 自主维护的 多语言系统，全站统一入口获取多语言对应内容） | Google 索引错乱                   | 爬虫模拟器对比各语言版本                                  |

## 二、技术方案设计

### 2.1 各层处理策略

#### 前端组件

- 建立 **共享组件包**（`@org/product-components`），放在 monorepo 中，所有站点通过 workspace 引用。
- 组件分为三层：
  - **展示层**（ProductHero、PriceBlock、FeatureList）：纯 props 驱动，SSG 友好。
  - **逻辑层**（useUserState、usePricing）：组合式函数，处理登录态 / 会员价 / A/B 实验。
  - **壳层**（ProductPageShell）：组装展示层 + 逻辑层，定义插槽供各站点注入差异内容。
- 各站点通过 **插槽 + 配置对象** 注入差异，而非 fork 组件。

#### 服务端渲染（SSR）

- 使用 Nuxt 的 `useAsyncData` + `useFetch`，确保数据在 SSR 阶段获取并序列化到 payload。
- 关键首屏数据（产品名、价格、主图）走 **SSR inline**，直接写入 HTML。
- 非首屏数据（评论、推荐、用户评价）走 **客户端延迟加载**（`lazy: true`）。
- 用户状态（登录 / 会员价）：SSR 阶段读 cookie 判断，若无法判断则输出"游客态"占位，客户端 hydration 后更新，避免闪烁。

#### 缓存策略

```
┌─────────────────────────────────────────────┐
│  层级            │  策略                     │
├─────────────────────────────────────────────┤
│  CDN 边缘        │  HTML: s-maxage=60,       │
│                  │  stale-while-revalidate=300│
│  SSR 响应缓存     │  Route Rules 按路由配置    │
│  API 数据缓存     │  Nitro 内置缓存 + Redis   │
│  静态资源         │  长期缓存 + content hash   │
└─────────────────────────────────────────────┘
```

- 价格等实时数据：API 层短缓存（30s），CDN 不缓存该接口。
- 产品描述 / 图片：长缓存 + CDN + 版本号。

#### 图片

- 格式：全部输出 AVIF/WebP，`<picture>` 降级 JPEG。
- 尺寸：通过 Nuxt Image（`@nuxt/image`）按需生成 `srcset`，移动端只拉 480w。
- LCP 图片：**预加载**（`<link rel="preload" as="image">`），不用 `lazy`，设置 `fetchpriority="high"`。
- 禁止首屏使用 `background-image`（无法被 LCP 候选）。
- CDN 开启图片自动格式协商。

#### 第三方脚本

- **分类治理**：

| 类型    | 加载策略                      | 示例           |
| ----- | ------------------------- | ------------ |
| 关键业务  | SSR 内联或 `<head>` 同步       | 支付 SDK（仅支付页） |
| 重要非关键 | `requestIdleCallback` 延迟  | 分析 / 埋点      |
| 营销追踪  | `IntersectionObserver` 触发 | 广告像素、转化追踪    |
| 实验平台  | `<head>` 同步但最小化           | A/B 实验脚本     |

- 所有第三方脚本统一通过 **`useThirdPartyScript`** **组合函数** 管理，支持延迟加载、错误兜底、CSP 合规。
- 支付 SDK 单独处理：仅在用户点击"购买"时动态 `import()`，不在首屏加载。

### 2.2 SSR / SSG / CSR 分层

```
┌──────────────────────────────────────────────────────┐
│  内容区块          │  渲染模式    │  理由              │
├──────────────────────────────────────────────────────┤
│  产品标题/描述      │  SSG        │  稳定，SEO 必须     │
│  产品主图           │  SSG        │  首屏 LCP 核心      │
│  结构化数据 JSON-LD │  SSG        │  SEO 必须           │
│  价格（标准价）     │  SSR        │  实时性要求中等      │
│  价格（会员价）     │  CSR        │  依赖登录态         │
│  用户评价/评论      │  CSR (lazy) │  非首屏，不影响 SEO  │
│  推荐商品           │  CSR (lazy) │  非首屏             │
│  A/B 实验变体       │  SSR+边缘   │  需首屏即时生效      │
│  支付按钮/入口      │  SSG        │  结构固定，交互 CSR  │
│  营销活动 Banner    │  SSR        │  运营需实时更新      │
│  埋点脚本           │  CSR (idle) │  不阻塞首屏         │
└──────────────────────────────────────────────────────┘
```

**核心原则：** 搜索引擎需要看到的内容 → SSG/SSR；用户交互才需要内容 → CSR；不紧急的内容 → 懒加载。

### 2.3 兼顾多维目标

**SEO 保障：**

- 所有 SSG 页面的 meta / JSON-LD / hreflang / canonical 在构建时生成，CI 中用爬虫校验。
- SSR 页面通过 `useHead` 确保服务端输出完整。
- 改版前后用 Screaming Frog 全站爬取对比，确保 URL、状态码、结构化数据零变化。

**LCP 优化路径（目标 ≤ 2.0s）：**

1. 预连接关键域名（CDN、图片 CDN）→ `<link rel="preconnect">`。
2. 预加载 LCP 图片 → `fetchpriority="high"` + `preload`。
3. 关键 CSS 内联（Nuxt 的 `renderSSRHead` 自动处理），非关键 CSS `media="print" onload="this.media='all'"`。
4. 首屏 JS 体积控制：Tree-shaking + 动态 import 非首屏组件，目标首屏 JS < 150KB gzipped。
5. 服务端响应优化：开启 Brotli 压缩，Nitro 开启 `compressPublicAssets`。
6. 第三方脚本全部推迟到 `window.onload` 或 `requestIdleCallback` 之后。

**支付入口稳定性：**

- 支付按钮 HTML 结构在 SSG 阶段输出，不依赖 JS hydration 即可见。
- 点击事件通过 `event delegation` 绑定，hydration 完成前用户点击不会丢失（记录到队列，hydration 后回放）。
- 支付 SDK 加载失败 → 降级为表单跳转支付（兜底链路）。

**用户状态：**

- SSR 阶段：读取 cookie 中的 session token → 调 API 获取用户态 → 输出对应价格。
- 超时或失败：输出"登录后可见"占位，客户端补全。
- Hydration：对比 SSR 输出和客户端状态，差异时平滑更新，不触发 CLS。

**多语言：**

- 每个语言版本独立构建（SSG）或独立路由（SSR）。
- `hreflang` 标签在 `<head>` 中完整输出，CI 自动校验所有语言版本互相引用正确。
- 文案通过 i18n JSON 文件管理，构建时注入，不在组件中硬编码。

## 三、AI 参与边界

### 3.1 可交给 AI 辅助执行的工作

| 工作 | AI 角色 | 约束 |
|------|---------|------|
| 组件迁移脚本 | 批量生成旧组件 → 新组件的代码转换 | 每个转换必须配单元测试 |
| 多语言文案提取 | 扫描组件中的硬编码文案，生成 i18n key | 人工确认 key 命名规范 |
| 图片优化 | 批量转换格式、生成 srcset、注入 Nuxt Image 组件 | 人工抽查 LCP 图片 |
| SEO meta 生成 | 根据产品数据批量生成 title / description / JSON-LD | 人工审核结构化数据正确性 |
| 性能审计 | 跑 Lighthouse CI，生成报告，标注回归项 | 人工判断是否需修复 |
| 测试用例生成 | 为共享组件生成 Vitest 单元测试 | 人工 review 边界 case |
| 跨站点 diff 分析 | 对比多站点同一组件的实现差异 | 人工决策统一到哪个版本 |
| 文档生成 | 生成组件 API 文档、迁移指南 | 人工确认准确性 |

### 3.2 必须人工完成的判断

| 判断项 | 理由 |
|--------|------|
| **支付链路变更确认** | 涉及资金安全，任何改动必须人工逐行 review + 回归测试 |
| **SEO 结构化数据变更** | JSON-LD 结构变更可能影响搜索排名，需 SEO 负责人确认 |
| **渲染模式选择（SSG vs SSR vs CSR）** | 需要结合业务场景、数据实时性、运维成本综合判断 |
| **灰度比例和回滚决策** | 线上风险判断需要业务 owner 拍板 |
| **CSP 策略调整** | 安全策略变更需安全团队审批 |
| **A/B 实验流量分配** | 影响营收，需产品和数据团队确认 |
| **缓存 TTL 设定** | 需平衡实时性和性能，需业务方确认 |

### 3.3 防止 AI 批量修改破坏关键路径的措施

1. **变更范围限制**：AI 生成的代码变更必须在 PR 中标注影响范围（哪些文件、哪些组件），CI 自动检测是否触及关键路径文件（支付、SEO 相关）。
2. **自动门禁**：
   - 触及 `payment/`、`seo/`、`structured-data/` 目录的 PR 自动添加 `requires-human-review` label，阻止自动合并。
   - AI 生成的 PR 必须通过全量自动化测试才能进入 review 队列。
3. **快照对比**：每次 AI 批量修改后，自动运行视觉回归测试（Playwright screenshot diff），对比首屏关键区域。
4. **渐进式合并**：AI 生成的变更按站点、按组件分批合并，不全量一次性合入。每批合并后跑完整回归。
5. **人工 reviewer 分配**：关键路径的 PR 必须至少一位业务 owner + 一位技术 owner approve。

## 四、验收与上线

### 4.1 质量门禁设计

```
代码提交 → ① Lint + Type Check → ② Unit Test → ③ Build Check
         → ④ SEO 验证 → ⑤ 性能基线 → ⑥ E2E 关键路径 → ⑦ 视觉回归
         → Staging → ⑧ 支付链路全量回归 → ⑨ 人工验收
         → 灰度发布 → ⑩ 监控观察 → 全量
```

| 门禁 | 工具 | 通过标准 |
|------|------|---------|
| ① Lint + Type Check | ESLint + Vue TSC | 0 error |
| ② Unit Test | Vitest | 覆盖率 ≥ 80%，0 failed |
| ③ Build Check | `nuxt build` | 构建成功，首屏 JS < 150KB gz |
| ④ SEO 验证 | Screaming Frog / 自建爬虫 | meta / JSON-LD / hreflang / status code 零差异 |
| ⑤ 性能基线 | Lighthouse CI | 移动端 LCP ≤ 2.0s，CLS ≤ 0.1，TBT ≤ 200ms |
| ⑥ E2E 关键路径 | Playwright | 支付入口可点击 → 弹窗加载 → SDK 初始化成功 |
| ⑦ 视觉回归 | Playwright screenshot diff | 首屏像素差异 < 0.5% |
| ⑧ 支付链路回归 | E2E + 沙箱环境 | 完整支付流程走通（沙箱支付成功） |
| ⑨ 人工验收 | PM + QA | 功能 / 样式 / 文案 / 交互确认 |
| ⑩ 灰度监控 | Sentry + Real User Monitoring | 错误率不升高，LCP p75 达标 |

### 4.2 验证矩阵

| 维度 | 验证方式 | 频率 |
|------|---------|------|
| 代码正确性 | TypeScript 类型检查 + ESLint + 单元测试 | 每次 PR |
| 构建完整性 | CI 全站点构建 + 产物体积检查 | 每次 PR |
| SEO | 全站爬取对比（URL / 状态码 / meta / JSON-LD / hreflang） | 每次发布前 |
| 性能 | Lighthouse CI + Web Vitals RUM | 每次 PR + 线上持续 |
| 支付链路 | E2E 沙箱全流程 | 每次发布前 + 灰度期间每日 |
| 视觉回归 | 截图 diff（首屏 + 关键组件） | 每次 PR |
| 多语言 | 各语言版本页面爬取 + hreflang 互引校验 | 每次发布前 |
| 跨站点一致性 | 共享组件版本检查 + 各站点功能对齐测试 | 每次发布前 |

### 4.3 灰度、监控与回滚

#### 灰度策略

```
阶段         │ 流量比例   │ 持续时间   │ 观察重点
─────────────────────────────────────────────────
Canary       │ 1%         │ 4h        │ 错误率、支付失败率
小流量       │ 5%         │ 24h       │ LCP p75、CLS、转化率
中流量       │ 25%        │ 48h       │ 转化率对比、SEO 爬取验证
大流量       │ 50%        │ 72h       │ 全指标对比 baseline
全量         │ 100%       │ -         │ 持续 RUM 监控
```

灰度按 **站点维度** 逐个推进，不在所有站点同时灰度。第一个站点选流量最小、风险最低的产品页。

#### 监控体系

| 指标 | 工具 | 告警阈值 |
|------|------|---------|
| JS 错误率 | Sentry | 较改版前升高 > 10% |
| LCP p75 | Web Vitals RUM / CrUX | > 2.5s |
| CLS p75 | Web Vitals RUM | > 0.15 |
| 支付成功率 | 业务监控 | 较改版前降低 > 0.5% |
| 页面可用性 | Uptime 监控 | 任何站点不可达 |
| SEO 索引状态 | Google Search Console | 索引量下降 / 爬取错误增加 |
| CDN 缓存命中率 | CDN 面板 | < 90% |

#### 回滚方案

- **代码级回滚**：保留上一版本 Docker 镜像 / 构建产物，10 分钟内回滚部署。
- **功能级回滚**：通过 Feature Flag 关闭改版组件，降级为旧版页面（无需重新部署）。
- **SEO 回滚**：保留旧版 HTML 快照，必要时通过 `robots` meta 快速下线新版。
- **回滚触发条件**（任一触发即回滚）：
  - 支付成功率下降 > 1%
  - JS 错误率上升 > 50%
  - LCP p75 > 4.0s
  - 页面不可用

## 使用的AI工具：
1. 扣子、kimi、豆包(免费)：需求拆解、技术方案生成
2. Trae、Cursor‌、 Claude Code、ChatGPT、：代码生成、性能优化建议

## 关键指令：
1. 需求拆解时，需根据项目背景、功能模块、技术栈等因素，将需求拆分为多个子需求。
  - 确保ai能够根据背景、功能模块、技术栈 拆分需求。
2. 技术方案生成时，需根据子需求，选择合适的架构模式、技术栈、工具等。
  - 确保ai能够根据每个需求的具体场景，选择合适的架构模式、技术栈、工具等。
3. 代码生成时，需根据技术方案，生成符合项目需求的代码。
  - 确保ai能够根据技术方案，生成符合项目需求的代码。
4. 检查并测试本次修改代码，保证没有任何致命问题，给出优化建议，并生成优化建议文档。

# 第三题：AI 产出审查与纠错
## 一、原方案核心风险 / 不完整点（逐条致命问题）1）SEO 风险
首屏以下全懒加载 + 价格 / 支付按钮放客户端接口：关键商业内容（价格、购买入口）不在首屏 HTML，爬虫抓取不到 / 权重极低。
关闭 SSR 复杂用户状态：内容可索引性下降、首屏文本缺失，排名与收录受损。
AI 批量改页面结构：极易破坏结构化数据（Schema）、H1 / 标题、内链，全站 SEO 雪崩。
2）LCP 与首屏关键元素
图片统一 lazy + 全懒加载：首屏图片也被懒加载，直接恶化 LCP（最大内容绘制）。
价格 / 支付按钮后置：核心转化元素不在首屏同步渲染，首屏意义失效。
无关键资源优先级：CSS / 字体 / 关键图未做预加载、未拆包，性能优化方向完全错。
3）价格展示与支付入口（合规 + 转化双崩）
价格 / 支付按钮放到客户端异步：白屏 / 无价格 / 无购买按钮成为常态，转化暴跌。
合规风险：电商 / 金融必须保证价格真实、稳定、可访问；异步失败 = 误导消费者。
无兜底：接口失败直接 “无价可看、无按钮可点”。
4）SSR / 水合 / 缓存
粗暴关闭 SSR 状态判断：水合不匹配（hydration mismatch）、页面闪烁、交互失效。
无分层渲染策略：首屏 / 非首屏、公开 / 用户态一锅端，缓存无法做。
无 CDN / 边缘缓存、无 ISR / 增量静态再生：性能提升不可持续。
5）第三方脚本加载策略
统一放底部 “一刀切”：

必须早期执行的脚本（埋点、A/B、权限、支付 SDK）延迟导致数据丢失 / 功能不可用。
无 async/defer/ 非阻塞 / 加载时机控制，底部依然阻塞。


无去重、无懒执行、无 consent（隐私合规）。
6）多站点批量修改风险
AI 批量替换页面结构：无差异、无校验、无回滚，一次上线全站崩溃。
不同站点业务、模板、域名、合规、第三方依赖完全不同，不可通用替换。
“先上线再观察”= 线上事故生产环境验证。
7）测试、监控、灰度、回滚（完全缺失）
无性能基准、无 LCP/CLS/TTI 指标。
无灰度、无分段发布、无回滚预案。
无错误监控（接口失败、水合报错、图片加载失败、第三方崩溃）。
8）AI 执行边界与人工审批
AI 被赋予生产发布、结构修改、上线决策权限，完全越界。
无评审、无验收、无人工卡点。
## 二、修正方案（可直接落地）1）SEO 与首屏关键内容（必须 SSR / 直出）
价格、库存、购买按钮、核心文案：必须 SSR 直出到 HTML，保证爬虫与首屏可见。
仅非首屏模块（评论、相关推荐、详情长文本）做懒加载 / 客户端加载。
保留并加固结构化数据（Product/Offer/Review），禁止 AI 批量修改。
2）LCP 优化：只懒加载 “非关键”，首屏强优先
首屏图片：禁止 lazy，使用：

width/height 防布局偏移
srcset + WebP/AVIF 自适应
preload/fetchpriority="high" 给 LCP 图


非首屏图片：loading="lazy" + 自动 WebP 降级兼容。
3）价格与支付：稳定优先、兜底优先
价格 / 按钮：SSR 直出默认值，客户端只做 “刷新 / 更新”，不做 “首次渲染”。
增加：接口超时兜底、缓存兜底、展示降级。
支付入口必须首屏可点击，不延迟、不阻塞。
4）SSR / 水合 / 缓存：分层渲染
不关闭 SSR，改为用户状态隔离：

公开页（商品详情）：纯 SSR + 强缓存
用户态（登录 / 购物车）：客户端局部水合


启用：CDN 缓存、ISR 增量更新、组件级缓存。
水合优化：仅交互组件水合，静态部分不水合。
5）第三方脚本：按 “职责” 加载，不一律底部
必须早期：async / 插入 head （如核心埋点、A/B 分流）。
可延迟：defer 或 交互触发 / 空闲时加载（聊天、统计、广告）。
统一治理：去重、错误捕获、 consent 合规、超时卸载。
6）多站点迁移：禁止 AI 批量替换结构
改为：模板抽象 + 组件共享 + 配置化，不修改页面 DOM 结构。
单站点验证 → 灰度 → 扩站点。
AI 仅做：代码提取、重复代码清理、注释、规则校验，不生成生产结构。
7）上线流程：强制四步（禁止先上线再观察）
基准测量：LCP/CLS/FID/TTI  baseline
测试环境全量回归
灰度 1%-10% 观测 10–30min
一键回滚 + 实时告警（错误、性能、转化）
8）AI 执行边界：明确 “不能做”
AI 不得：修改页面结构、修改 SEO 标签、决定是否上线、批量替换。
AI 只能：给出优化清单、代码片段建议、检测问题、生成报告。
所有涉及渲染 / 结构 / 入口变更必须人工评审 + 合并。
